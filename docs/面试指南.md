# 「知源」RAG 系统 —— 面试介绍与问答准备

## 一、项目介绍稿

### 一分钟版（开场）

> 我独立开发了 RAG 知识库问答系统「知源」。它把 PDF、Word、扫描件和图片解析成带页码、章节和字符范围的语义块，并向量化存入 pgvector。提问先归为闲聊、创作、知识、时效、混合五类语义意图，再由确定性策略选择直接回答、知识库、网络或混合路径；联网开关具有最高优先级。回答通过 SSE 逐 token 返回，事实依据使用稳定编号，相同资料复用同一编号；点击知识库引用可回到原文位置。前后端采用 FastAPI + Vue 3，可观察处理阶段与耗时，但不暴露模型内部思维链。

### 三分钟版（展开）

**背景与目标**：通用大模型不懂企业私域知识且容易幻觉，我做的这个系统让回答尽量基于用户上传的资料，资料不足时不伪造引用；没有资料且问题不具时效性时由模型直接回答，需要时效核验的问题才按联网开关使用网络。界面展示的是可观察处理阶段和引用依据。

**技术架构**（按数据流讲）：
1. **入库链路**：多格式解析——PDF 逐页判断文本层，扫描页自动渲染成图片走 OCR；Word 提取段落和表格；文本文件做编码探测（UTF-8/GBK/UTF-16）。然后是**语义切块**：按标题行（Markdown 标题、"第X章"、"一、"、"1.2."等）强制分段，标题归属后续内容，相邻段落合并到目标长度，块间保留句子级重叠，超长段落按句末标点切分，避免语义被拦腰截断。最后用 BGE-M3 向量化（1024 维多语言模型）存入 pgvector，建了 HNSW 索引。
2. **问答编排**：`ChatService` 集中编排。问题先归为闲聊、创作、知识、时效、混合五类，再由纯函数结合知识库状态和联网开关映射到 direct、kb、web、hybrid 四条路径。知识库路径先用 bge-m3 召回 8 个候选并按相似度 0.4 粗筛，再用 bge-reranker 按 0.3 精排；精排 0 命中时会触发查询改写并重试一次。
3. **记忆体系**：分层的——短期是最近 6 轮历史窗口，长期参考 MemGPT/mem0 思想，每轮后台增量合并出"摘要 + 事实要点"存库，生成时注入。
4. **可解释性**：服务在理解、路由、检索、精排、改写、联网和生成阶段追加 trace，前端展示处理过程、耗时和可点击编号引用。

**结果与攻坚**：端到端约 30 秒（瓶颈在外部 LLM API 延迟），检索环节不到 1 秒；实测英文提问能命中中文资料（相似度 0.66）。过程中还攻克了几个深层 bug，比如 pgvector 元数据 typmod 判断错误导致每次重启误清全库、PyTorch 2.6 weights_only 兼容性、HuggingFace 弱网离线加载（处理耗时从 5 分钟降到 19 秒）、CSS transform 创建包含块导致 fixed 弹窗被父容器锁死等。

## 二、高频追问与参考回答

### Q1：为什么选 bge-m3？和 bge-small-zh 比有什么区别？

> 最初用的 bge-small-zh-v1.5，512 维、纯中文。但实际资料中英文混排，且英文提问也要能查中文库，所以换成 bge-m3：1024 维、8192 token 上下文、100+ 语言。实测中英同义对相似度 0.67、英问中资料 0.66 有效命中。另外 bge v1.5 系列查询侧要加"为这个句子生成表示…"指令前缀，bge-m3 不需要，代码里做了条件判断。代价是模型 2.3GB 内存，我用懒加载单例控制。

### Q2：为什么要两级检索（召回+精排）？直接用向量相似度不行吗？

> 双编码器（bi-encoder）把 query 和文档独立编码，速度快但精度有限——我实测向量相似度上"领域近义但无关"的内容能到 0.52，和真相关的 0.54-0.73 落在同一区间，单靠阈值切不干净。交叉编码器（cross-encoder）把 query 和文档拼接后联合编码，能捕捉细粒度交互，实测相关 0.46+、无关 <0.06，区分度极好。但交叉编码器要逐对打分，不能建索引，所以只适合小候选集。因此架构是：HNSW 索引快速召回 8 个 → 精排逐对深判。这是标准的召回-精排权衡。

### Q3：阈值是怎么定的？

> 实验校准的。拿真实资料构造"相关/领域近义无关/泛无关"三组 query-doc 对，看分数分布：向量相似度相关 0.54-0.73、泛无关 0.28-0.38，中间地带留给精排，所以粗筛定 0.4（宽进）；精排相关 0.46+、无关 <0.06，间隔很大，定 0.3 很稳。还做了降级设计：reranker 模型缺失时退化为相似度排序，不阻断主流程。

### Q4：语义切块具体怎么做的？为什么不用固定长度切？

> 固定长度会把句子拦腰截断、把一个完整章节切碎，检索出来的片段语义不完整。我的方案：先空行分段规整；用正则识别标题行（Markdown #、中文章节"第X章/一、"、编号"1.2."、字母"A."），标题强制开新块且和后续内容保持同块——因为检索时"标题+正文"的片段自包含性更好；相邻段落合并到约 500 字，块间保留约 120 字的**句子级**重叠（从最后一个句末标点后截取，保证不截半句）维持上下文；超长段落按句末标点切分。过短的孤立起始块（如文档大标题）并入下一节，避免产生无意义小向量。

### Q5：意图识别怎么设计的？踩过什么坑？

> 第一版把语义意图和执行路径混成 `kb/web/chitchat`，导致“帮我写一段话”也可能先查库，联网限制还分散在节点里。重构后先用确定性强信号识别寒暄、创作和时效词，模糊问题再要求 LLM 按 JSON Schema 返回五类结构化结果；Pydantic 校验失败会降级为低置信度 knowledge。随后纯函数结合知识库是否可用、联网开关和置信度生成四类执行路径，因此业务规则可单测，联网开关也不会被任何节点绕过。

### Q6：RAG 怎么解决幻觉的？能完全解决吗？

> 缓解而非根除。生成 prompt 要求基于编号资料作答，服务端会删除不存在的引用并只返回实际被引用的来源；相同来源按稳定 key 去重。用户可点击编号核对网页或知识库原文位置。后续仍可增加逐句事实一致性校验和离线质量评测。

### Q7：为什么把编排收敛到 ChatService，而不是继续把逻辑散在接口里？

> 第一版把意图、联网开关、检索兜底和生成分散在多个节点里，测试时很难证明“关闭联网一定不会搜网”。现在我把查询理解、路由、检索、重排、改写、来源编号和流式事件收敛到 `ChatService`，其中路由是纯函数，四条执行路径都能用依赖注入做单测。这样既保留了状态流的可观察性，也让规则更容易改，比如“无资料且不具时效性的问题直接由模型回答”就是在路由策略里一处落地。

### Q8：记忆系统怎么设计的？

> 分层：短期记忆取最近 6 条消息格式化注入，保证即时连贯；长期记忆参考 MemGPT/mem0，每轮问答后由后台任务（不阻塞响应）让 LLM 把现有记忆和新对话增量合并成"摘要（≤300 字全局脉络）+ 要点（≤15 条关键事实）"，存 session_memories 表，生成时注入。解析失败保留旧记忆，不覆盖。难点在增量合并的 prompt 设计——要指示"保留仍有效的旧要点、删除过时项"。

### Q9：说说你印象最深的一个 bug。

> （推荐讲这个，展示排查深度）现象是**每次重启服务数据库就被清空**。代码里有个维度迁移逻辑：启动时检查 embedding 列维度是否等于配置值，不等就清库重建。检查方式读的是 pg_attribute 的 atttypmod，然后减 4——这是 varchar 的约定（typmod 存的是"长度+4"），但 pgvector 的 typmod **就是维度本身**，1024 - 4 = 1020 ≠ 1024，每次都误判成"维度变了"，于是每次重启都清库。修复是改用 `format_type()` 返回 `vector(1024)` 字符串直接比对。这个 bug 教训是：不能把一个类型的元数据约定想当然地套到另一个类型上，而且"幂等迁移"这种每次启动都跑的逻辑，一旦有错就是灾难性的——值得为它写测试。

### Q10：如果 QPS 上去了怎么扩展？

> 按层拆：模型层，bge-m3 抽成独立推理服务（或 vLLM/TEI 部署），多副本 + 批处理；DB 层，pgvector 单机够用到百万级，再往上换专用向量库（Milvus/Qdrant）或读写分离；编排层的 `ChatService` 无状态，可以随 FastAPI 实例水平扩展；入库是后台任务，可以换消息队列削峰。另外缓存 key 要包含问题、kb_id 和库版本，否则库更新后缓存会脏。

### Q11：这个项目有什么不足？

> ① SSE 降低了首字等待，但外部 LLM 仍决定总耗时；② 目前已有后端和前端回归测试、Git 分支与分段提交，依赖仍需锁版本；③ 仍以向量召回为主，缺 BM25 混合召回；④ 双模型常驻内存约 4GB，可考虑量化或按需卸载；⑤ 还需要 golden set 持续评估召回率、引用正确率和答案质量。

### Q12：为什么自己写切块/解析，不用 Unstructured/LlamaIndex？

> 核心诉求是可控和轻量：标题正则能针对中文文档特征（"第X章""一、"）精确适配，OCR 选 RapidOCR 纯 CPU 可跑、中文效果好，都不引重型依赖。LlamaIndex 抽象层级高，定制切块逻辑反而要绕。当然如果资料格式更野（HTML/PPT/复杂表格），Unstructured 更省力——这是按场景做的选型，不是重复造轮子。

## 三、可延伸的技术谈资（按需展开）

- **pgvector HNSW**：近似最近邻，m/ef_construction 参数、余弦距离算子 `<=>`、`vector_cosine_ops`；对比 IVFFlat：HNSW 查询快且不用先灌数据建索引
- **bge-m3 的三种能力**：我用了 dense 向量，它还支持 sparse（学习型词权重，可替代 BM25）和 multi-vector（ColBERT 式），可以做混合检索——这是现成的演进方向
- **MemGPT/mem0 思想**：LLM 内存分页→分层记忆；核心是"记忆是数据不是上下文"，由 LLM 自己管理读写
- **PCA 可视化**：SVD 截断取前两主成分，附带解释方差比，采样上限 3000 防内存问题
- **前端 CSS 包含块陷阱**：transform/filter/perspective 都会创建包含块，fixed 元素相对它而非视口定位——弹窗必须 append-to-body（Teleport 到 body）
- **PyTorch 2.6 weights_only**：安全默认值导致旧 .bin checkpoint 加载失败，官方路径是转 safetensors
