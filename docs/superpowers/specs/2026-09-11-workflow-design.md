# 编排与会话工作流完善

用户将优先级调整为编排层和其他工作流，并要求已通过且未受影响的测试不再重复。本轮保留已完成的评测成果，不追加模型实验。

## 已确认目标与实现选择

沿用 ChatService 的依赖注入设计，将普通与流式入口收敛到同一个阶段执行器。两个入口仅在生成输出方式上不同，理解、路由、检索、证据策略与引用收尾共享。相比迁移框架或加入自治循环，这次选择可直接复用既有路由和接口协议的方案。

每个阶段追加状态与耗时，流式接口及时发送阶段状态与 trace；结果包含 run_id、answer_mode、warnings。日志只记运行标识、阶段、结果和耗时。检索/联网一方不可用时，混合请求保留另一方来源并标明缺失。改写最多一次，关闭联网的原有策略保持有效。

没有足够资料的 kb/web/hybrid 请求返回确定性的资料不足答复，不调用生成器编造业务事实；需要时效核验但联网关闭时提示限制。未选择知识库、没有资料的普通问题仍可直接回答。根据资料写作不能误判成无需资料的普通创作，带问候前缀的实质问题不能被当成闲聊。

提示词使用独立 system 规则与 JSON 数据边界，记忆和检索内容作为参考数据，不作为操作指令；引用校验始终运行，包括零来源的情况。这个措施不声称完全防住提示注入，也不声称编号合法就代表事实一致。

会话的用户/助手消息改为一次事务提交；失败不留下半个问答。记忆任务携带历史与现有记忆的指纹，在写回事务内核对；历史编辑、会话删除、新消息和其他记忆更新导致旧任务放弃写回。PostgreSQL 使用按会话的事务级 advisory lock，模型调用在锁外执行。编辑助手消息时清理过期引用/trace，编辑历史时清除长期摘要；不自动重生成后续答案。

流式消费者关闭后显式关闭上游迭代器；断开期间尚在阻塞的同步网络调用仍受上游超时约束，不声称瞬时停止推理。未收到 done 的流不写成完整答复。存储失败转换为结构化 error，不返回成功终止事件。

## 文件职责与验收

- app/chat_service.py：共享阶段执行器、有限改写、缺少证据/部分来源降级、run_id/耗时。
- app/query_understanding.py：显式资料写作和问候前缀边界。
- app/main.py：system 规则接入、事务写回、条件记忆更新、流关闭和结构化存储错误。
- app/db.py：原子问答存储、历史/记忆指纹与条件保存。
- tests/test_workflow.py / tests/test_conversation_workflow.py：本轮新增行为。
- 更新受影响的流协议/持久化旧用例；仅执行这些用例及相关检索筛选契约，已通过的其他测试不重跑。

验收关注行为：同步与流式来源/路由一致；kb 零命中不调用 LLM；混合检索一方失败保留另一方；阶段耗时存在；错误无内部机密；上游 close 被调用；数据库回滚；过期记忆不复活。真实数据库部署与负载测试不在本轮声称范围内。
