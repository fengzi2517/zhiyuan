# 部署指南：本机与阿里云

更新：2026-09-14。适用于 schema v2、生产 `ChatService`、独立 Worker 和会话附件。命令中的示例域名、目录和密码需要换成自己的值；本次整理未在阿里云实际部署。

## 1. 部署前准备

服务由浏览器前端、FastAPI、Worker、PostgreSQL+pgvector、uploads 原件存储和模型缓存组成。API 与 Worker 必须使用同一数据库、同一 uploads 根目录。API 在查询时也会加载嵌入/精排模型，不能只给 Worker 配置模型缓存。

Python 建议从 Dockerfile 的 3.12 基线开始；本机现有环境可继续使用。Node.js 建议 22.12+；前端通过 `npm ci` 使用 lockfile。Python requirements 没有全量锁版本，首次安装要记录实际依赖，不能宣称任意新版本组合都经过验证。

CPU 可以运行；单机试用建议从 4 核/16 GB 内存及充足模型空间起步，这只是容量规划起点，不是压测结论。API/多个 Worker 各有自己的模型进程副本；内存不足先减少 Worker 数与 EMBEDDING_BATCH_SIZE，不要直接堆进程。

配置文件从 [.env.example](../.env.example) 创建。不要覆盖已有 `.env`，也不要上传它。安装前准备可用 LLM API Key；TAVILY_API_KEY 留空时无法成功联网检索。

## 2. Windows 本机首次运行

在 PowerShell 执行：

```powershell
git clone https://github.com/fengzi5422/rag-app.git
cd rag-app
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

用编辑器填写 `.env`，默认本地数据库地址为 `postgresql+psycopg://rag:rag@127.0.0.1:5435/rag`。开发 Compose 使用演示密码；只用于受控本机，不用于公网数据库。

```powershell
docker compose up -d postgres
docker compose ps
```

### 下载与预热模型

应用按模型 ID 加载 Hub 缓存。用 `HF_HOME` 配置根目录，`snapshot_download` 写入其中标准 `hub/models--.../snapshots/...` 结构。不能仅下载到 `.hf-cache/BAAI/bge-m3` 然后假设模型 ID 会找到它。参考 [Hugging Face 下载说明](https://huggingface.co/docs/huggingface_hub/guides/download)。

```powershell
$env:HF_HOME = Join-Path (Get-Location) '.hf-cache'
$env:HF_HUB_OFFLINE = '0'
.\.venv\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download('BAAI/bge-m3'); snapshot_download('BAAI/bge-reranker-base')"
$env:HF_HUB_OFFLINE = '1'
.\.venv\Scripts\python.exe -c "from app.embeddings import embed_texts; print(len(embed_texts(['预热检查'])[0]))"
```

最后应打印 `1024`。网络不可达时使用自己可访问的模型仓库或受控代理，下载完成再设置离线；不要保留临时断点下载脚本，也不要直接修改 Hub blob。严格复现需记录下载返回的快照 revision；默认下载的最新版本会变化。

### 迁移、账号与三个进程

```powershell
.\.venv\Scripts\python.exe -m app.migrate
.\.venv\Scripts\python.exe -m app.admin bootstrap admin
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

bootstrap 交互设置至少 12 字符密码；已有管理员不重复 bootstrap。没有公开注册、没有预置管理员密码。新增用户可使用管理员界面或 `python -m app.admin create-user NAME`。

另开终端，在项目根目录：

```powershell
.\.venv\Scripts\python.exe -m app.worker
```

再开终端：

```powershell
cd frontend
npm ci
npm run dev -- --host localhost --port 5173 --strictPort
```

访问 `http://localhost:5173`。不要混用 localhost 和 127.0.0.1。若改端口，同步修改 TRUSTED_ORIGINS。离开开发环境后不应暴露 Vite 开发服务器。

Linux 裸机也可运行：用 `python3 -m venv .venv` 创建环境，以 `.venv/bin/python` 替换上述 Python 路径；其余模块命令相同。

## 3. 配置含义

| 配置 | 用途 |
|---|---|
| DATABASE_URL | 本机/API/Worker 的数据库连接 |
| LLM_BASE_URL / LLM_API_KEY / LLM_MODEL | 辅助调用和默认模型配置 |
| LLM_REASONING_EFFORT | 辅助分类/改写/摘要/记忆的模式，SenseNova 默认 none |
| CHAT_MODEL_PROFILES | 服务端模型能力注册表，详见[多模态配置](多模态聊天与会话附件.md) |
| LLM_TIMEOUT_SECONDS / LLM_MAX_RETRIES | 模型超时与 SDK 重试；默认 60 秒/0 次 |
| HF_HOME / HF_HUB_OFFLINE | 标准模型缓存位置及离线加载 |
| EMBEDDING_BATCH_SIZE | 默认 4，CPU 入库峰值内存控制 |
| UPLOAD_DIR | 文档和附件原件目录，API/Worker 一致 |
| APP_ENV / TRUSTED_ORIGINS | production 使用 Secure Cookie；允许的浏览器 Origin |
| JOB_LEASE_SECONDS / JOB_MAX_ATTEMPTS | 默认 120 秒租约、最多 3 次尝试 |

改环境配置后重启 API 与 Worker。前端 `VITE_API_BASE_URL` 是**构建时**配置，修改后要重建前端；留空会落回 `http://当前hostname:8000`，不适用于正式 HTTPS 发布。

## 4. 阿里云公网部署：HTTPS 同源方案

### 4.1 服务器、域名和端口

准备 Linux ECS、Docker Engine/Compose、Git、Nginx、Node/npm；域名解析到 ECS 公网 IP，安装该域名的有效 TLS 证书。中国内地站点需按自身情况完成备案等要求，具体以云平台提示为准。

安全组与系统防火墙只开放业务需要的 80/443；SSH 22 限制为维护来源。PostgreSQL 不映射公网，8000 只绑定环回；不要把模型和 uploads 当静态文件公开。安全组操作参考[阿里云官方说明](https://www.alibabacloud.com/help/en/ecs/user-guide/start-using-security-groups)。

本文使用 `rag.example.com`，统一入口为 `https://rag.example.com`，API 前缀为 `/api`。真实证书路径和域名必须替换。

### 4.2 配置后端

```bash
git clone https://github.com/fengzi5422/rag-app.git
cd rag-app
cp .env.example .env
chmod 600 .env
```

编辑 `.env`，填写真实 API Key，并设置：

```dotenv
APP_ENV=production
POSTGRES_PASSWORD=替换成足够长的随机密码
DEPLOY_DATABASE_URL=postgresql+psycopg://rag:URL编码后的同一密码@postgres:5432/rag
TRUSTED_ORIGINS=https://rag.example.com
HF_HUB_OFFLINE=1
```

密码包含 `@:/#%` 等字符时需按 URL 用户信息部分编码，不能直接拼接。部署 Compose 通过 environment 覆盖 DATABASE_URL、HF_HOME=/models、UPLOAD_DIR=/data/uploads。它使用独立项目 `rag-deploy` 和独立卷，**不会自动使用本地开发库的数据**。

```bash
docker compose -f docker-compose.deploy.yml build
docker compose -f docker-compose.deploy.yml up -d postgres
docker compose -f docker-compose.deploy.yml run --rm migrate
```

先把模型下载到共享 models 卷，覆盖离线设置仅用于此命令：

```bash
docker compose -f docker-compose.deploy.yml run --rm --no-deps -e HF_HUB_OFFLINE=0 worker python -c "from huggingface_hub import snapshot_download; snapshot_download('BAAI/bge-m3'); snapshot_download('BAAI/bge-reranker-base')"
docker compose -f docker-compose.deploy.yml run --rm --no-deps worker python -c "from app.embeddings import embed_texts; print(len(embed_texts(['warmup'])[0]))"
docker compose -f docker-compose.deploy.yml up -d web worker
docker compose -f docker-compose.deploy.yml exec web python -m app.admin bootstrap admin
curl --fail http://127.0.0.1:8000/health/ready
```

下载必须能访问模型上游；也可将标准 Hub 缓存完整转移到模型卷并校验权限。镜像以 uid 10001 运行，挂载目录需可读写。不要通过 chmod 777 或把服务改为 root 掩盖权限错误。

### 4.3 发布前端和 Nginx

```bash
cd frontend
npm ci
VITE_API_BASE_URL=https://rag.example.com/api npm run build
sudo mkdir -p /var/www/rag-app
sudo cp -a dist/. /var/www/rag-app/
cd ..
sudo cp deploy/nginx.conf.example /etc/nginx/conf.d/rag-app.conf
# 编辑 rag-app.conf：真实 server_name、证书 fullchain 和 private key 路径
sudo nginx -t
sudo systemctl reload nginx
```

模板位于 [deploy/nginx.conf.example](../deploy/nginx.conf.example)。`/api/` 的 proxy_pass 末尾 `/` 会剥离前缀；前端不能同时又把 `/api` 加到后端路由上。关闭代理缓冲，让 SSE 内容逐段传送；上传上限 60m 容纳 50 MB 附件与 multipart 开销。参考 [Nginx 代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。

证书必须在 `nginx -t` 前已经就位。HTTP 入口仅重定向 HTTPS；没有证书时先在本机完成验收，不要用生产 Secure Cookie 的登录失败来判断密码错误。TLS 证书续期由现有证书管理工具维护。

### 4.4 公网验收

1. `curl --fail https://rag.example.com/api/health/ready` 返回 ready。
2. 浏览器登录，Network 中请求发往同源 `/api/...`，不出现 mixed-content/CORS 错误。
3. 创建自己的库，上传 TXT、文本 PDF 和 DOCX，等待 done；检索引用能打开原件。
4. 上传会话图片：视觉开启直接识图，关闭使用 OCR；无文字图像应明确提示切换视觉。
5. 流式回答逐段出现；删除会话后原件接口不可访问；第二个用户无法获取第一个用户的私有会话。
6. 只在专用测试数据上演示 Worker 中断和租约恢复，不用业务资料做破坏性测试。

## 5. 更新、运维和备份

更新前保存当前代码 SHA、镜像摘要、环境变量、实际 pip 依赖和数据备份。升级文档可能涉及模型、向量维度或路径变更，不能只执行 git pull。

```bash
git pull --ff-only
docker compose -f docker-compose.deploy.yml build
docker compose -f docker-compose.deploy.yml stop web worker
docker compose -f docker-compose.deploy.yml run --rm migrate
docker compose -f docker-compose.deploy.yml up -d web worker
# 按 4.3 使用同一 VITE_API_BASE_URL 重建并发布前端
docker compose -f docker-compose.deploy.yml logs --tail=100 web worker
```

schema v2 迁移为追加式建表/加列，使用 advisory lock 串行迁移；多连接 DDL 不承诺整体回滚。维度不匹配拒绝启动，不自动删库。失败时先修复原因，再重跑迁移。不要直接把代码退回不认识当前 schema 的版本。

备份需同一停写窗口：停止 web/worker，保持 PostgreSQL 运行；数据库与 uploads 一起备份。以下为 Linux 部署 Compose 示例，不要在 PowerShell 旧版用文本重定向写二进制 dump：

```bash
mkdir -p backups
set -e
docker compose -f docker-compose.deploy.yml stop web worker
docker compose -f docker-compose.deploy.yml exec -T postgres pg_dump -U rag -d rag -Fc > backups/rag.dump
docker compose -f docker-compose.deploy.yml run --rm --no-deps -v "$PWD/backups:/backup" --user 0 worker tar -czf /backup/uploads.tar.gz -C /data uploads
docker compose -f docker-compose.deploy.yml up -d web worker
```

上述一次性备份命令用 root 仅写备份挂载，业务服务仍为 uid 10001。备份包含私人文件，应加密并限制读取；示例文件名固定，正式使用时间戳防止覆盖历史备份。

恢复到**新主机上的空库和空 uploads 卷**，保持 web/worker 停止。配置固定 `name: rag-deploy`，在现有主机换一个目录不会自动得到新卷；同机演练需为所有命令统一指定不同的 `-p` 项目名，并安排不同的监听端口。以下按新主机编写，每一步成功才继续：

```bash
docker compose -f docker-compose.deploy.yml up -d postgres
set -e
docker compose -f docker-compose.deploy.yml exec -T postgres pg_restore -U rag -d rag --no-owner --exit-on-error < backups/rag.dump
docker compose -f docker-compose.deploy.yml run --rm --no-deps -v "$PWD/backups:/backup:ro" --user 0 worker tar -xzf /backup/uploads.tar.gz -C /data
docker compose -f docker-compose.deploy.yml run --rm migrate
docker compose -f docker-compose.deploy.yml up -d web worker
```

不要把恢复命令对着已有业务库执行。原件路径在 DB 中为绝对路径；同样 `/data/uploads` 路径可直接恢复。Windows → Linux 迁移必须停写、转移原件，校验文件后映射 documents.storage_path、chat_attachments.storage_path 和 image_path；同时涉及附件 claim-specific 图片名，不能只修改 Document 路径。未提供自动跨路径恢复工具，完成映射前不要启动 Worker。

定期预览/执行清理：

```bash
docker compose -f docker-compose.deploy.yml exec web python -m app.operations cleanup
docker compose -f docker-compose.deploy.yml exec web python -m app.operations cleanup --apply
```

它根据数据库引用清理孤立原件，24 小时未发送附件会过期；并非自动后台定时任务，需要安排运维调度。`down` 停服务不等于备份；不要使用 `down -v` 删除数据卷。

## 6. 排错速查

| 现象 | 首先检查 |
|---|---|
| 数据库连接等待/拒绝 | docker compose ps、5435/容器内5432、DATABASE_URL、数据库是否健康 |
| 提示先迁移 | 用相同环境执行 app.migrate，确认 API/Worker 都是 schema v2 代码 |
| 下载超时/离线找不到模型 | HF_HOME 标准缓存结构、revision完整、下载时 OFFLINE=0、启动前预热 |
| 入库一直 queued | Worker 是否运行；API和Worker DB/UPLOAD_DIR是否一致 |
| running 后失败 | Worker stage/error_type；内存、原件格式、PDF页数/尺寸及模型缓存 |
| 登录 403 | Origin 精确匹配、HTTPS Secure Cookie、同hostname，前端携带CSRF |
| 一次性显示整段回答 | Nginx/CDN 是否缓冲，/api/路由是否真正代理到SSE |
| 附件上传 413 | 单文件/总量上限与 Nginx 60m，不要只提高代理而绕过应用限制 |
| 页面还用旧模型列表 | API重启、前端刷新；模型 registry 配置是否有效 |
| 简单闲聊很慢 | trace生成耗时、首token、thinking_mode、供应商排队，不重复跑检索评测代替LLM诊断 |

健康检查只覆盖进程与数据库版本，不代表供应商、OCR 或所有模型已经可用。日志避免打印密钥、完整聊天和隐藏推理；应用日志保留阶段及类型，生产 Compose 轮转日志。

代理来源边界：主机 Nginx 经 Docker 网桥访问 Uvicorn 时，默认可信代理范围可能不包含该来源，按 IP 登录限流会将多人视为同一连接来源。正式上线前核实实际网桥和代理地址，再精确配置可信代理；不要无条件信任 `*` 或客户端伪造的 X-Forwarded-For。

## 7. 定向验证与复现记录

```powershell
docker compose -f compose.integration.yml up -d --wait
$env:TEST_DATABASE_URL='postgresql+psycopg://rag_test:isolated_test_only@127.0.0.1:5445/rag_test_foundations'
.\.venv\Scripts\python.exe -m pytest integration_tests -q --basetemp=.test-tmp-integration
```

测试必须使用专用 `rag_test_` 库，会 TRUNCATE 应用表。不要将业务库改名绕过防护。无变更时不反复运行已通过的套件。

供应商验证是单独的显式操作：`python scripts/verify_multimodal_provider.py --live` 使用合成算术/图片，消耗账户额度。保存环境版本、Git SHA、模型 revision、匿名测试结果与时间，不把密钥写入日志或 Git。

已有功能验证见[多模态记录](多模态聊天与会话附件.md)；本次整理只验证文档链接、Git 发布内容及配置静态契约，未声称重新执行云部署或全套应用测试。
