# 知源 · RAG 知识库问答系统 —— 技术报告

> 版本：v2.0（本地闭环优化版）｜更新日期：2026-09-05
> 本报告面向希望**从 0 到 1 复刻**本系统的开发者，理清全部核心逻辑链条。

---

## 一、项目概述

「知源」是一个本地闭环的 RAG（检索增强生成）知识库问答系统：

- **多格式资料入库**：PDF（含扫描件）、Word、图片、TXT、Markdown，统一解析 → 语义切块 → 本地向量化 → PostgreSQL(pgvector) 存储
- **多语言检索**：BGE-M3 多语言模型（1024 维），中英文混检，实测英文提问可命中中文资料
- **智能问答编排**：五类语义意图与四条执行路径分离，联网开关由纯路由策略统一执行
- **过程透明**：前端展示可观察的处理阶段、路由理由和耗时，并通过编号引用定位依据
- **流式交互**：SSE 返回 `status → route → token* → sources → trace → done`，异常以 `error` 结束
- **多轮会话**：会话历史持久化 + 分层长期记忆（摘要 + 事实要点）

### 技术栈总览

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite + Element Plus + ECharts | 三视图：对话 / 资料管理 / 向量库管理 |
| 后端 | FastAPI + Uvicorn | REST API，后台任务异步入库 |
| 编排 | ChatService + 纯路由策略 | 集中完成意图、检索、重排、联网、引用和流式事件 |
| 向量模型 | BAAI/bge-m3（本地） | 1024 维，8192 token 上下文，中英混合 |
| 重排模型 | BAAI/bge-reranker-base（本地） | 交叉编码器精排，不可用时自动降级 |
| OCR | RapidOCR (onnxruntime) | 图片/扫描件识别，CPU 可跑 |
| 数据库 | PostgreSQL 18 + pgvector（Docker） | 向量存储 + HNSW 索引 |
| LLM | SenseNova（OpenAI 兼容 API） | 意图识别 / 改写 / 生成 / 记忆合并 |
| 联网搜索 | Tavily API | 时效性问题直连、知识库不足兜底 |

## 二、核心逻辑链条

整个系统由六条逻辑链构成，理解这六条链就理解了整个项目。

### 链路 1：文档入库（数据流）

```
用户上传 ──► /upload ──► 后台任务异步处理（不阻塞响应）
                            │
                            ▼
                    parser.py  解析
                    ├─ 图片(png/jpg/…) ──► RapidOCR
                    ├─ PDF ──► 文本层提取；单页文本 < 20 字 → 按"扫描页"
                    │          渲染 200dpi 图片 → OCR 兜底
                    ├─ docx ──► 段落 + 表格（表格行拼接为制表符文本）
                    └─ txt/md ──► 编码探测（utf-8 → gbk → utf-16，容错解码）
                            │
                            ▼
                    chunker.py  语义切块
                    ├─ 空行分段 → 段落规整
                    ├─ 标题行（markdown / 第X章 / 一、/ 1.2.）强制开新块，
                    │   标题与其后内容保持同块
                    ├─ 相邻段落合并至 ~500 字，块间保留 ~120 字句子级重叠
                    └─ 超长段落按句末标点切分，不字符硬切
                            │
                            ▼
                    embeddings.py  向量化（BGE-M3，1024 维，归一化）
                            │
                            ▼
                    db.py  save_chunks ──► pgvector（HNSW 余弦索引）
```

**关键设计**：
- 语义切块以"标题归属"和"句子边界"为核心，避免语义被拦腰截断；块间重叠保证上下文连贯
- PDF 每页独立判断文本层，扫描页自动 OCR，混合型 PDF 也能完整提取
- 上传后立即返回 doc_id，状态机 `pending → done/failed` 前端可轮询

### 链路 2：问答编排（服务层状态流）

```
用户问题
  │
  ▼
understand_structured：五类语义意图
  │
  ▼
decide_route：结合知识库是否可用、联网开关和置信度，得到四条执行路径
  │
  ├─ direct：直接生成，不伪造引用编号
  ├─ kb：向量召回 → 粗筛 → rerank → 0 命中时改写查询并重试一次
  ├─ web：Tavily 搜索 → 过滤安全 URL → 编号引用
  └─ hybrid：知识库来源与网络来源合并编号
  │
  ▼
generate / stream_generate：注入历史、长期记忆和编号来源，返回回答与处理过程
```

**五类语义意图**：`chitchat`、`create`、`knowledge`、`current`、`mixed`。强信号先由确定性规则处理，模糊问题再要求 LLM 输出 JSON Schema；结构化结果异常时降级为低置信度 `knowledge`。

**四条执行路径**：`direct`、`kb`、`web`、`hybrid`。没有可用资料且问题不具时效性时直接由模型回答；时效问题在联网开启时走网络，联网关闭时不会访问 Tavily；低置信度且有知识库时优先用知识库约束回答。

**知识库检索链**：精排 0 命中 → 查询改写重试（1 次）→ 仍 0 命中则携带空来源生成，不伪造引用编号。混合路径会同时收集知识库和网络来源。

### 链路 3：两级检索（召回 → 精排）

| 阶段 | 模型 | 候选数 | 阈值 | 作用 |
|---|---|---|---|---|
| 召回粗筛 | bge-m3 双编码器 | top 8 | 相似度 ≥ 0.4 | 快速海选，HNSW 索引加速 |
| 精排 | bge-reranker 交叉编码器 | ≤ 8 | 相关性 ≥ 0.3 | 逐对深判，区分度极佳 |

**实测分数分布**（用于校准阈值）：
- bge-m3：相关 0.54–0.73，领域近义无关 ~0.52，泛无关 0.28–0.38
- reranker：相关 0.46+，无关 < 0.06（区分度远优于向量相似度）

**降级设计**：reranker 模型缺失时自动退化为相似度排序，不阻断主流程。

### 链路 4：分层记忆

```
短期：chat_messages 表，最近 6 条格式化为 Q:/A: 注入每次生成
       └─ 支持前端查看 / 编辑 / 删除历史消息

长期：session_memories 表（每个 session 一条）
       └─ 每轮问答后，后台任务调 LLM 增量合并：
          【现有记忆】+【新对话】→ 新【摘要(≤300字)】+【要点(≤15条)】
       └─ 生成 prompt 时注入：摘要 + 要点
```

参考 MemGPT / mem0 的分层记忆思想：短期窗口保证即时连贯，长期摘要+事实保证跨轮次记忆不丢失。

### 链路 5：处理过程追踪（trace）

`ChatService` 在每个可观察阶段向 `trace` 追加条目，随 `/chat` 或 `/chat/stream` 响应返回，前端以"处理过程"样式展开：

| 阶段 | 展示内容 |
|---|---|
| understand | 语义意图、判定理由 |
| route | direct / kb / web / hybrid 及路由理由 |
| retrieve | 检索 query 和最终保留条数 |
| rerank | 精排候选数量；模型不可用时记录降级模式 |
| rewrite / web_search | 改写后的检索词 / 网络检索条数 |
| generate | 回答生成完成 |

这让系统从"黑盒"变为"白盒"：用户能看到答案是怎么来的。

### 链路 6：前端交互契约

| 前端操作 | API | 说明 |
|---|---|---|
| 新建/删除向量库 | POST/DELETE /kbs | 多库隔离，kb_id 贯穿全链路 |
| 上传资料 | POST /upload?kb_id= | ≤ 20MB，后台异步入库 |
| 查看提取文本 | GET /documents/{id}/content | 验证解析/OCR 效果 |
| 向量可视化 | GET /kbs/{id}/vectors | PCA 降二维散点（SVD，≤3000 采样） |
| 问答 | POST /chat | 返回 answer + intent + trace + sources |
| 会话管理 | GET/DELETE /sessions 等 | 历史列表/加载/编辑/删除 |
| 参数设置 | /chat 请求体 | top_k / sim_threshold / web_enabled |

## 三、数据库设计

```
knowledge_bases(id, name unique, description, created_at)
documents(id, kb_id, filename, status, content, created_at)   -- content 存提取全文
chunks(id, kb_id, doc_id, content, embedding vector(1024))
    └─ HNSW 索引: ix_chunks_embedding_hnsw (vector_cosine_ops)
    └─ B-tree 索引: kb_id, doc_id
chat_messages(id, session_id, role, content, created_at)
    └─ 复合索引: (session_id, created_at)
session_memories(id, session_id unique, summary, facts, updated_at)
```

**幂等轻量迁移**（init_db 启动时执行）：
1. `CREATE EXTENSION IF NOT EXISTS vector` + 建表
2. 为存量表补充 kb_id / content 列
3. **维度迁移**：`format_type()` 比对 embedding 列实际类型，与配置 `vector(1024)` 不符才清库重建
   > ⚠️ 踩坑记录：pgvector 的 `atttypmod` 就是维度本身，不能用 varchar 的 `typmod-4` 约定判断——曾导致每次重启误清全库的严重 bug
4. HNSW 索引 `CREATE INDEX IF NOT EXISTS`

## 五、从 0 到 1 复刻指南

### 5.1 环境要求

- Python 3.10+、Node.js 18+、Docker Desktop
- 内存 ≥ 16GB（BGE-M3 ~2.3GB + reranker ~1.1GB 常驻）
- 外网访问（LLM API + Tavily + 模型下载）

### 5.2 步骤

**① 启动数据库**

```bash
docker compose up -d     # pgvector/pgvector:pg18，宿主机 5435 端口
```

> 本机原生 PG 占 5432、其他容器占 5433/5434，故用 5435。PG18 镜像 volume 必须挂 `/var/lib/postgresql`。

**② 配置环境变量**

```bash
cp .env.example .env
# 填入 LLM_API_KEY（SenseNova）与 TAVILY_API_KEY（tavily.com 免费 1000 次/月）
```

**③ 安装后端依赖**

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

**④ 下载本地模型（最大坑点，务必细读）**

模型文件放项目内 `.hf-cache/`，代码启动时设 `HF_HUB_OFFLINE=1` 离线加载（避免每次联网检查超时——曾导致向量化卡 5 分钟+）。

```bash
# 方式一：huggingface-cli（国内注意代理，出错时清空 HTTP_PROXY/HTTPS_PROXY 重试）
huggingface-cli download BAAI/bge-m3 --local-dir .hf-cache/BAAI/bge-m3
huggingface-cli download BAAI/bge-reranker-base --local-dir .hf-cache/BAAI/bge-reranker-base
```

踩坑清单（均已踩过，提前规避）：
- bge-m3 主权重文件名是 `pytorch_model.bin`（2.27GB），不是 `model.safetensors`（404）
- 下载中断产生损坏文件时，先排查进程文件锁再删除
- **PyTorch 2.6+ 默认 `weights_only=True`**，.bin 格式可能报 `invalid load key`：
  转成 safetensors 即可 —— `from safetensors.torch import save_file; save_file(torch.load('pytorch_model.bin', map_location='cpu', weights_only=True), 'model.safetensors')`

**⑤ 启动后端**

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

**⑥ 启动前端**

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173
```

**⑦ 验证闭环**

```bash
# 上传资料（任意 pdf/docx/txt/图片）
curl -F "file=@施工安全规范.txt" "http://localhost:8000/upload?kb_id=1"

# 查看入库状态与提取文本
curl http://localhost:8000/documents

# 问答（answer + 处理过程 trace + 编号引用来源）
curl -X POST http://localhost:8000/chat -H "Content-Type: application/json" ^
  -d "{\"question\": \"高处作业有哪些安全要求？\", \"session_id\": \"u1\"}"
```

浏览器访问 `http://localhost:8000/docs` 查看 Swagger；前端上传资料 → 对话提问 → 查看处理过程，并点击正文编号核对引用。

### 5.4 兼容迁移与定位数据

应用启动时只执行 `ADD COLUMN IF NOT EXISTS` 类型的增量迁移，不删除旧文档或旧消息。新增字段保存文档原件路径、切块页码/章节/字符范围，以及每条助手消息的语义意图、执行路径、编号来源、处理过程、耗时和完成状态。历史会话因此可以恢复当时的来源和过程信息。

旧版本文档仍可检索，但原数据不包含原件路径与精确切块位置。需要点击引用回到页码或章节时，应重新上传并入库该文档。

## 六、已解决问题档案（排错经验）

| # | 问题 | 根因 | 解决 |
|---|---|---|---|
| 1 | 自定义 GET /docs 路由不可达 | 被 FastAPI 内置 Swagger 路由屏蔽 | 移除自定义路由 |
| 2 | 检索全无关时仍直送生成 | 未清空 docs，改写机制永不触发 | rerank 0 命中时正确置空并计数重试 |
| 3 | **每次重启数据库被清空** | pgvector typmod 判断误用 varchar 的 `-4` 约定 | 改用 `format_type()` 精确比对 |
| 4 | 模型加载卡 5 分钟+ | 每次向 HF 发在线检查请求，弱网超时重试 | `.hf-cache` + `HF_HUB_OFFLINE=1`，降至 19s |
| 5 | PyTorch 2.6 加载报 invalid load key 'E' | weights_only 与 .bin 不兼容 + 损坏文件实为 15B 错误页 | 校验文件大小、转 safetensors |
| 6 | 弹窗高度锁死在父卡片内 | 父容器入场动画的 transform 创建包含块，`position: fixed` 失效 | 全部 el-dialog 加 `append-to-body` |
| 7 | 可视化图表过矮 | vh/clamp 在弹窗内计算失真 | JS 读 `window.innerHeight` 动态算像素高度 |
| 8 | 服务进程 0xC0000005 崩溃 | 双模型 + 系统内存压力超提交上限 | 控制并发模型进程；可选 fp16 减半内存 |
| 9 | 429 限流 | LLM API 限流 | 指数退避重试（10s/20s） |

## 八、后续演进方向

1. **LLM 延迟优化**：意图识别与生成占端到端耗时 95%+，可换更低延迟模型或并发化
2. **内存优化**：BGE-M3 fp16 加载（~2.3GB → ~1.2GB）
3. **缓存**：问答缓存 key 需纳入 kb_id 与库版本（当前仅问题文本，库更新后缓存可能过期）
4. **测试与工程化**：补充单测/集成测试、锁定依赖版本、Git 版本管理
5. **多路召回**：关键词(BM25) + 向量混合召回，提升召回率
