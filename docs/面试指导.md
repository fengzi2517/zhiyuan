# 多模态 RAG 项目面试指导

整理日期：2026-09-14。代码讲解基线：`5dfec36`；面向大模型应用开发、RAG 开发和 Python 后端岗位。
本文是结合仓库实现的练习材料，不是线上规模、商业收益或个人贡献的证明。简历中的“负责”应替换为自己实际完成的内容。
检索实验另有版本：2026-09-10 的固定基线对应编排改造前代码，不能冒充当前版本端到端结果。

## 1. 先记住项目的真实边界

- 当前 HTTP 问答主链是 [main.py](../app/main.py) → [ChatService](../app/chat_service.py)，同步和 SSE 共用执行逻辑。
- [graph.py](../app/graph.py) 是旧 LangGraph 实现；可以讲迁移历程，不能把它说成当前生产主编排。
- 文档处理是 PostgreSQL 持久任务加独立 Worker；不是 Redis/Celery 队列，也没有证明大规模分布式吞吐。
- 知识库使用 PostgreSQL + pgvector、BGE-M3 1024 维向量和 BGE 交叉编码器重排。
- 支持原生图片输入、OCR、会话私有附件和有预算的全文摘要；不是视频理解或视觉向量检索系统。
- 有代码测试和固定合成语料检索实验；没有真实业务答案正确率、万人并发或商业收益数据。

## 2. 两种项目介绍

### 30 秒版本

“这是一个支持知识库和会话附件的多模态 RAG 应用。后端用 FastAPI、PostgreSQL 和 pgvector，文档经独立 Worker 解析、切块、向量化；问答使用向量召回、交叉编码器重排和 SSE 流式输出。我重点关注任务中断恢复、引用定位和用户权限，也做了固定检索实验。实验显示重排能减少无答案问题返回资料，但会漏掉部分可回答问题，所以我没有把重排直接宣传成准确率提升。”

### 3 分钟版本

“项目解决的是上传资料后进行可追溯问答，以及在会话里临时分析文件和图片的问题。用户既能查知识库，也能使用当前会话私有附件；回答保留引用位置，方便回到原文核对。

离线链路上，上传原件后先持久化文档和任务，再由 Worker 解析 PDF、DOCX 或文本，按字符窗口与结构边界切块，使用 BGE-M3 编码到 pgvector。耗时计算在数据库事务外执行。任务通过行锁领取、租约续期和领取令牌校验处理 Worker 中断，最终块、正文和任务状态在同一事务提交。

在线链路上，当前是 ChatService，共用同步和流式实现。先理解问题，再根据知识库可用性和联网设置决定路线；知识库默认召回 8 个候选、向量阈值 0.4，重排阈值 0.3，默认保留 4 个。结果为空时最多改写重试一次。资料不足有明确输出模式，引用编号会校验，但这并不等于逐句事实验证。

多模态部分按请求选择模型、思考模式和视觉能力。图片可直接进入视觉模型，关闭视觉则只用 OCR。长附件问答走会话内检索，全文总结则遍历所有分组并受时间和调用次数限制，不能用 top-k 片段伪装成全文摘要。

验证方面，固定实验是 12 文档、24 块、60 问题的合成语料。在保留集上，dense 的 Recall@4 是 1.0，dense 加重排是 0.9167；无答案空检索率从 0 变成 1.0。这说明阈值存在漏检与误返回的权衡。它不是当前版本端到端准确率，也不包含 HNSW 与生成。我下一步会补真实标注集、答案忠实度评测和权限过滤后的索引召回实验。”

## 3. 三条诚实简历样例

1. 开发 FastAPI + Vue 多模态知识库问答应用，串联文件解析、BGE-M3 向量检索、交叉编码器重排和 SSE 输出，提供原文位置引用及会话私有附件。
2. 实现 PostgreSQL 持久入库队列，使用 `SKIP LOCKED`、租约续期和领取令牌校验限制过期 Worker 提交；结合事务保证文档块与任务完成状态一致，并支持失败重试。
3. 建立 12 文档、24 块、60 问题的固定检索实验；保留集重排 Recall@4 为 0.9167，无答案空检索率为 1.0000，识别重排阈值导致的漏检，并记录数据、模型及源码指纹以支持复现。

第三条需注明实验是合成小样本、检索层评测。不要改写为“准确率 91.67%”“生产拒答率 100%”或“召回率提升至 91.67%”。

## 4. 从基础到架构的 30 个追问

回答时采用“实际实现 → 为什么 → 失败边界 → 下一步验证”的顺序；先说 30 秒核心回答，再按追问展开。

### A. RAG 与检索基础

**01｜为什么用 RAG，而不是微调？**

RAG 把可更新知识作为检索资料输入，适合需要引用和权限隔离的文档问答。微调更适合调整行为或任务能力，不能自动解决实时知识、删除资料和访问控制。本项目没有训练模型，实际采用本地嵌入模型、重排模型与外部生成接口。
追问练习：资料被删除后怎样避免继续检索？回答数据库删除和权限范围，并区分已生成历史的生命周期。
证据：[db.py](../app/db.py)、[jobs.py](../app/jobs.py)。

**02｜切块参数是什么，为什么不直接按 token？**

默认 `size=500`、`overlap=120`，是字符预算，结合段落、句子及解析单元处理，并保留页码、章节、字符位置。字符切分简单可解释，但不等于模型 token 数，也没有证明该参数最优。
追问练习：表格和跨页条款可能被拆散，应如何构造失败样例？可以提出结构感知切块实验，但明确尚未完成通用版式理解。
证据：[chunker.py](../app/chunker.py)、[parser.py](../app/parser.py)。

**03｜BGE-M3 在这里用了哪些能力？**

实际通过 SentenceTransformer 获取归一化的 1024 维稠密向量；查询侧对 BGE-M3 不额外加旧版 BGE 指令前缀。没有启用 BGE-M3 的稀疏或多向量检索能力，不能因为模型支持就声称项目实现了混合检索。
追问练习：换嵌入模型为什么往往要重新编码整库？空间变化即使维度相同也不保证可比较。
证据：[embeddings.py](../app/embeddings.py)、[config.py](../app/config.py)。

**04｜余弦检索如何实现？**

查询向量进入参数化 SQL，按 pgvector `<=>` 余弦距离升序取候选，相似度为 `1 - distance`。数据库初始化建立 HNSW 索引，但实际是否使用、权限过滤后的召回表现，需要看查询计划和专项实验。
追问练习：不能用本地精确扫描基线推断 HNSW 的 ANN 召回率。
证据：[db.py](../app/db.py) 的 `search_chunk_sources`、`init_db`。

**05｜为什么召回后还要重排？**

双编码器适合先召回，交叉编码器联合读取问题和片段进行精排。本项目先做向量阈值筛选，再重排，最后应用重排阈值并截取 top-k。重排不能找回根本没进入候选集的证据，也可能过滤正确证据。
追问练习：增加候选数会增加哪些成本？嵌入检索结果传输、重排计算和可能的延迟。
证据：[chat_service.py](../app/chat_service.py) 的 `_select_kb_rows`。

**06｜重排挂了怎么办？**

模型加载失败或执行异常可降级到向量相似度；`_rerank_applied` 用来区分实际重排与降级，避免错误地用重排阈值筛向量分数。trace 记录降级模式。固定评测反而要求失败即报错，不把降级结果算成重排实验。
追问练习：为什么两个阈值不能混用？两个模型的分数语义与分布不同。
证据：[embeddings.py](../app/embeddings.py)、[chat_service.py](../app/chat_service.py)、[run.py](../evaluation/run.py)。

**07｜查询改写是不是每次调用？**

不是。当前知识库选择结果为空时才尝试改写，最多重新检索一次；改写失败、空结果或与原问题相同就停止。这样限制额外调用与无限循环，但改写也可能偏离专有编号，因此需要样例验证。
追问练习：固定实验是否覆盖此优化？没有，报告明确排除查询改写。
证据：[chat_service.py](../app/chat_service.py) 的 `_retrieve_kb_steps`。

**08｜如何减少幻觉？**

系统把资料作为不可信参考数据，要求 grounded 模式依据资料回答；不足时使用 `insufficient_evidence`，并提供确定性的资料不足说明。引用编号会校验，但有合法编号仍可能引用错事实，不能声称消灭幻觉。
追问练习：下一步增加逐句证据支持检查、人工标注或答案忠实度评测，均应标为计划。
证据：[chat_service.py](../app/chat_service.py)、[sources.py](../app/sources.py)。

### B. 编排、流式与多模态

**09｜项目是不是 LangGraph Agent？**

仓库保留旧 LangGraph 文件，当前 `/chat` 与 `/chat/stream` 调用的是 ChatService。它是明确的问答工作流，不是能自主执行任意工具的通用 Agent。可以解释旧实现与新服务边界，不能混淆入口。
追问练习：何时才值得恢复图编排？复杂分支、持久检查点或人工介入需要明确收益和实现计划。
证据：[main.py](../app/main.py)、[chat_service.py](../app/chat_service.py)、[graph.py](../app/graph.py)。

**10｜分类服务出错会怎样？**

问题理解结果经结构校验；异常时回退保守理解并生成 warning。路由还考虑知识库可用性和联网开关，而非完全服从模型标签。缺少可核验资料时，不把“调用成功”当成“有依据”。
追问练习：联网未配置和搜索失败都会导致无资料，应看 trace、warnings 和回答模式定位。
证据：[query_understanding.py](../app/query_understanding.py)、[routing.py](../app/routing.py)、[search.py](../app/search.py)。

**11｜SSE 输出有哪些事件？**

包括 `status`、`route`、`trace`、`token`、`sources`、`done` 和 `error`。同步与流式使用同一 `_execute`，降低行为漂移；HTTP 流式封装在 `done` 发给前端之前保存消息，保存失败则发 error。
追问练习：已经收到 token 并不代表消息已经持久化；前端必须等待终态。
证据：[main.py](../app/main.py) 的 `chat_stream`、[sse.py](../app/sse.py)。

**12｜有流式为什么首字还慢？**

首字之前仍有问题理解、附件准备、检索、重排以及供应商等待。`generate.first_token_ms` 从生成阶段开始测量，不是浏览器端到端 TTFT；status 事件也不是答案首 token。应该分别观察阶段 trace、服务端首 token 和浏览器接收时间。
追问练习：现有延迟脚本比较直接模型与工作流，但不是完整 HTTP/浏览器性能测试。
证据：[chat_service.py](../app/chat_service.py)、[benchmark_chat_latency.py](../scripts/benchmark_chat_latency.py)。

**13｜快速和深度思考是怎么切换的？**

通过逐请求模型 profile 选择模式选项；默认 SenseNova 快速模式传 `reasoning_effort=none`，深度模式省略该参数，采用供应商默认行为。辅助理解、改写和摘要使用辅助 LLM 配置，不会自动跟随聊天深度模式。
追问练习：不能把所有供应商的“deep”视为相同协议，也不能把空选项等同于关闭推理。
证据：[model_profiles.py](../app/model_profiles.py)、[llm.py](../app/llm.py)、[多模态说明](多模态聊天与会话附件.md)。

**14｜为什么不展示隐藏思考正文？**

应用只消费最终回答内容，不展示、存储或记录供应商隐藏推理正文。模型元数据保存实际选择，便于区分模式；模式验证脚本只记录是否出现推理字段等诊断信息。
追问练习：trace 是业务执行阶段，不是模型内部思维链。
证据：[llm.py](../app/llm.py)、[verify_multimodal_provider.py](../scripts/verify_multimodal_provider.py)。

**15｜OCR 与原生视觉有什么区别？**

视觉开关打开且模型支持时，规范化 JPEG 以 base64 图像内容送给生成模型；关闭时仅使用 OCR 文字。无可用 OCR 文字时阻止文字模式发送。原生视觉失败不会悄悄改走 OCR；PDF 始终通过文本层或扫描页 OCR。
追问练习：图表可附截图，但项目没有保证复杂图表识别正确，也不是图像 embedding 检索。
证据：[file_pipeline.py](../app/file_pipeline.py)、[attachment_context.py](../app/attachment_context.py)。

**16｜长文档总结为什么不能只做 top-k？**

top-k 适合问题相关证据查找，无法代表全文覆盖。当前摘要最多处理 19.2 万字符、16 组，遍历所有组后压缩，并记录覆盖组数；全程预算 90 秒、20 次调用、每次至多 20 秒。超限明确失败，覆盖所有组也不保证所有细节保留。
追问练习：区分“遍历覆盖”“语义无遗漏”和“答案事实正确”三个不同目标。
证据：[attachment_context.py](../app/attachment_context.py) 的 `SummaryBudget`、`summarize_full_text`。

**17｜上下文预算如何控制？**

profile 默认文本预算 24000 字符，应用还限制图片数量、附件数量及文件大小。字符数不是供应商 token 数，需要为系统提示、输出和图片预留空间；不能把字符预算当成严格 tokenizer 级容量证明。
追问练习：不同语言、JSON 转义和图片会让字符到 token 的估算失真。
证据：[model_profiles.py](../app/model_profiles.py)、[main.py](../app/main.py) 的 `messages`。

### C. 队列、一致性与权限

**18｜为什么不在上传请求里直接解析？**

解析/OCR/模型加载耗时不稳定。当前先保存原件、文档和持久任务，独立 Worker 执行，API 返回可查询任务。计算在事务外，避免长期占用数据库锁；重启进程后任务仍在数据库中。
追问练习：文件系统和数据库不是同一个 ACID 事务，需要原子文件写入、异常清理和运维回收共同处理。
证据：[jobs.py](../app/jobs.py)、[worker.py](../app/worker.py)、[operations.py](../app/operations.py)。

**19｜两个 Worker 如何避免同时领取？**

领取在短事务中使用 `FOR UPDATE SKIP LOCKED`，选择到期排队任务或过期 running 任务，再更新状态、尝试次数和令牌。被其他事务锁住的行跳过。它支持竞争领取，但不等于已测过大规模吞吐或严格全局公平性。
追问练习：文档和附件是各自的任务资源；Worker 交替检查两类队列。
证据：[jobs.py](../app/jobs.py) 的 `claim`、[attachments.py](../app/attachments.py)、[worker.py](../app/worker.py)。

**20｜租约过期后旧 Worker 恢复，如何避免污染？**

每次领取生成新的随机 `claim_token`。完成、失败和续租必须同时满足 running、令牌相等、租约未过期，并锁住任务行。新 Worker 接管后旧令牌无法提交。这是领取代次隔离；不是单调递增的全局 fencing 序列。
追问练习：旧 Worker 仍可能消耗计算资源；保证的是受保护提交被拒绝，不是保证计算只发生一次。
证据：[queue_lease.py](../app/queue_lease.py)、[jobs.py](../app/jobs.py) 的 `complete`。

**21｜为什么使用数据库时钟？**

PostgreSQL 使用 `clock_timestamp()` 判断租约，减少跨进程本机时钟差异；与事务开始时间固定的时间函数区分。续租周期为租约时长的约三分之一，默认租约 120 秒，配置下限 15 秒。
追问练习：数据库不可用仍可能导致续租失败，最终提交必须再验证所有权。
证据：[queue_lease.py](../app/queue_lease.py)、[worker.py](../app/worker.py)。

**22｜幂等是指上传同一个文件不重复吗？**

不是。普通上传没有按内容哈希去重。文档成功提交受租约保护，在同一事务替换该文档块并更新状态；附件“保存到知识库”以 `(attachment_id, kb_id)` 唯一约束和既有记录实现幂等。应分别说明这些语义。
追问练习：不要把重试安全写成全系统 exactly-once，外部计算和文件写入可能发生多次。
证据：[jobs.py](../app/jobs.py) 的 `complete`、[attachments.py](../app/attachments.py) 的 `AttachmentPromotion`、`promote`。

**23｜删除资源与运行任务会发生竞态吗？**

会，所以不能只检查请求开始时的存在性。知识库删除取消相关任务并撤销令牌；完成时锁库再查任务所有权。附件移除、会话删除与提交遵循会话锁再任务行锁，旧提交不能复活删除资源。
追问练习：统一锁顺序降低死锁风险；不要把“降低”说成所有数据库死锁都不存在。
证据：[jobs.py](../app/jobs.py) 的 `delete_knowledge_base`、[attachments.py](../app/attachments.py)、[db.py](../app/db.py)。

**24｜权限是在检索之后过滤吗？**

当前为登录用户生成可访问知识库范围，并把范围带入 SQL 条件；空范围直接返回空，不先搜全库再在答案中隐藏。原件和附件接口也验证归属；附件同时绑定用户与会话。
追问练习：应用层权限过滤不等于已配置 PostgreSQL RLS，也不等于物理多租户隔离。
证据：[main.py](../app/main.py) 的 `_authorized_chat`、[db.py](../app/db.py) 的 `search_chunk_sources`、[auth.py](../app/auth.py)。

**25｜长时间生成期间权限被撤销怎么办？**

生成前会再次检查资料、知识库和登录会话，持久化时也重新校验访问权。用户与助手消息在同一事务保存，并标记附件已使用。不能承诺撤权能收回已经发给客户端的 token，或者保证任意时刻中止供应商内部计算。
追问练习：这是典型检查与使用之间的竞态，要准确说明检查点及剩余窗口。
证据：[main.py](../app/main.py) 的 `check_access`、[db.py](../app/db.py) 的 `save_exchange`。

**26｜Cookie 登录如何防跨站请求？**

服务端保存登录令牌哈希；非安全方法同时校验可信 Origin 和 CSRF 请求头。知识库角色、会话归属是独立于登录的授权步骤。仅有登录不代表能访问所有文档。
追问练习：部署时 HTTPS、Cookie 配置和前后端 hostname 需要协同，不能只谈前端按钮隐藏。
证据：[auth.py](../app/auth.py)、[auth_routes.py](../app/auth_routes.py)。

### D. 评测、运维与工程判断

**27｜0.9167 到底是什么指标？**

是固定保留集 24 个有答案问题上的平均 Recall@4；其定义是前 4 个不同块命中的相关块数除以该题相关块数。不是答案正确率。该轮重排 MRR@4、nDCG@4 恰好也为 0.9167，不能推广为这些指标永远相同。
追问练习：为什么无答案问题不放入 Recall 分母？其相关块集合为空，另用空检索率统计。
证据：[评测报告](../evaluation/reports/baseline-v1/summary.md)、[metrics.py](../evaluation/metrics.py)。

**28｜为什么重排 Recall 降了，还保留它？**

该样本上它降低了无答案问题返回资料的情况，但漏掉一些可回答问题，且增加延迟。是否保留应由业务对误返回、漏答、耗时的容忍度决定，不能只看单一数字。当前只能报告默认阈值结果，不能宣称方案最优。
追问练习：仅用 dev 调阈值，固定方案后验 test；已反复查看的 test 应补新的独立集。
证据：[evaluation/README.md](../evaluation/README.md)、[results.json](../evaluation/reports/baseline-v1/results.json)。

**29｜如何排查“上传后一直处理中”？**

先确认 Worker 存活，再查任务状态、attempts、租约和 stage 日志；分辨模型加载、OCR、向量化与提交卡住。`/health/live` 只说明 API 活着，`/health/ready` 检查数据库/模式就绪，不是完整模型健康检查。
追问练习：任务过期由领取流程恢复，不能只重启 API；重试耗尽需要定位原因后手动重试。
证据：[operations.py](../app/operations.py)、[worker.py](../app/worker.py)、[jobs.py](../app/jobs.py)。

**30｜如果需求增长十倍，先改什么？**

先补真实请求画像、数据库查询计划、Worker 资源和分阶段延迟，再决定是否批处理、增加 Worker、拆分模型服务或引入其他队列。当前没有足够规模数据支持先上微服务、分布式缓存或多数据库。
追问练习：提出可验证假设，例如重排是主要成本，就先比较候选数与质量/延迟曲线；这些是后续实验。
证据：[worker.py](../app/worker.py)、[chat_service.py](../app/chat_service.py)、[评测报告](../evaluation/reports/baseline-v1/summary.md)。

## 8. 自测和欠缺项

面试前应能独立完成以下检查，而不是背诵类名：

- [ ] 找到真实 HTTP 入口，说明为何不是旧 graph 主链。
- [ ] 画清原件、文档、块、任务、附件和会话的生命周期关系。
- [ ] 解释检索范围如何在 SQL 中限制，及生成/持久化为何重复检查权限。
- [ ] 演算租约过期后两个 Worker 的合法和非法提交。
- [ ] 说清普通重复上传、任务重复执行和附件保存幂等的区别。
- [ ] 解释 0.9167 的分母、实验版本和局限，不把它说成准确率。
- [ ] 区分全文分组覆盖与摘要事实完整性；区分 OCR 与原生视觉。
- [ ] 能以日志阶段、任务状态和 trace 定位一次失败，而非反复重启。

**已经实现但仍有边界：** 引用校验不是事实验证；租约防旧提交不是 exactly-once；字符预算不是 token 精确计量；应用层授权不是数据库 RLS；本地 HNSW 索引存在不代表已验证近似召回质量。

**尚需补充的工程证据：** 真实业务独立标注集、当前版本端到端答案质量、复杂 OCR/图表人工验收、HNSW 与权限过滤联合作用、并发压力/资源成本曲线、长期故障恢复与备份还原演练记录。

**可提出但不要写成已完成：** BM25 混合召回、领域专有编号策略、tokenizer 精确预算、逐句证据支持检查、模型服务拆分、集中监控告警和更全面的提示注入对抗评测。每项都应先给出需要解决的真实失败样例，再决定实现优先级。
